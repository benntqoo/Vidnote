## §1 【环境】MSVC 选版错误 —— 任何需要编译 C/C++ 的 crate 都会失败

### 症状

```
cl-rs: command did not execute successfully (exit code 2)
```
配合 `cl.exe` 找不到 `<stdio.h>` 之类的头文件。首个撞上的 crate 通常是 `vswhom-sys`。

### 根因

本机装了两套 VS，`cc-rs` 按「**版本更新优先**」选中了残缺的那套：

```
D:\IDE\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.44.35207\
    └── 只有 Auxiliary / bin / lib，**缺 include 目录**（被裁剪）
```

### 判据

不确定是不是这个问题时，看**完整**的那套 VS 有没有被打包工具裁掉 include：

```bash
ls "C:/Program Files (x86)/Microsoft Visual Studio/2019/BuildTools/VC/Tools/MSVC/14.29.30133/include" | head
```

### 修法

在 `app-ui/src-tauri/.cargo/config.toml`（**本机专用，已 gitignore**）设四个环境变量，指向完整的那套：

```toml
[env]
CC  = '...\2019\BuildTools\VC\Tools\MSVC\14.29.30133\bin\HostX64\x64\cl.exe'
CXX = （同上）
INCLUDE = '...\MSVC\14.29.30133\include;<Windows Kits>\Include\10.0.26100.0\{ucrt,shared,um,winrt,cppwinrt}'
LIB     = '...\MSVC\14.29.30133\lib\x64;<Windows Kits>\Lib\10.0.26100.0\{ucrt,um}\x64'
```

**四个变量必须一起给，不能只给 `CC`/`CXX`。** cc-rs 只在**自行探测到完整安装**时才注入 `INCLUDE`/`LIB`；一旦你显式给了 `CC`，它就不再探测，于是那两个变量会是空的。

**反证（证明 `CC` 确实被采信）**：把 `CC` 指向一个不存在的路径，会立刻报 `failed to find tool`。

### 为什么不走 `vcvars64.bat`

本机 `reg.exe` 被安全策略禁用 → `vcvarsall.bat` 查不到 Windows SDK 版本 → 导出的 `INCLUDE` 里只有 MSVC 的 include、缺 UCRT/SDK 部分，照样缺 `stdio.h`。

### 边界（已经实测，别重复怀疑）

- 本文件只补 C/C++ **编译**。Rust 自己的链接仍由 rustc 探测 VS 2022 的 `link.exe` 与 `lib`——MSVC 14.x 各版本二进制兼容，**这条路径可用**（`cargo build` 已通过）。
- **彻底修复**：用 VS Installer 给 VS 2022 补装「使用 C++ 的桌面开发」工作负载，补回 include，然后删掉该文件。

## §2 【环境】`schemars` 报 E0107 —— 构建脚本的运行时探测不可靠

### 症状

```
error[E0107]: struct takes 3 generic arguments but 2 generic arguments were supplied
  --> schemars-0.8.22\src\lib.rs:12:32
   |
12 | pub type Map<K, V> = indexmap::IndexMap<K, V>;
   |                                ^^^^^^^^ supplied 2 generic arguments
note: struct defined here, with 3 generic parameters: `K`, `V`, `S`
  --> indexmap-1.9.3\src\map.rs:76:12
```

### 因果链（逐环节实证过）

1. `tauri-utils` 打开了 `schemars` 的 `preserve_order` feature → schemars 用 `indexmap::IndexMap<K, V>`（**两个**泛型参数）。
2. `schemars 0.8.22` 声明的是 `indexmap = { version = "1.2", features = ["serde-1"] }`——`serde-1` 只是 `["serde"]`，**不含 `std`**；而 `indexmap 1.9.3` 的 `[features]` 里**压根没有 `default` 兜底**。于是编译 indexmap 时 `CARGO_FEATURE_STD` 不是「已设置」。
3. `indexmap 1.9.3` 的 `build.rs` 因此走 fallback，用 `autocfg` **实际调用 rustc 探测** sysroot 里有没有 `std` crate，来决定要不要 emit `has_std`：
   ```rust
   match std::env::var_os("CARGO_FEATURE_STD") {
       Some(_) => autocfg::emit("has_std"),        // 不探测，直接发
       None => autocfg::new().emit_sysroot_crate("std"),  // ← 真的去 spawn rustc
   }
   ```
4. `IndexMap<K, V, S = RandomState>` 这个**默认类型参数只在 `#[cfg(has_std)]` 下存在**（`src/map.rs:70`）。探测失败 → 没有默认 `S` → 第 1 步的两参写法变成「expected 3 generic arguments」。
5. 探测失败的原始证据（给 `build.rs` 打临时诊断补丁、把结果写进文件拿到，因为**非本地依赖的 `cargo:warning` 会被 cargo 隐藏**）：
   ```
   CARGO_FEATURE_STD=false
   probe_raw=ERR 所有的管道范例都在使用中。 (os error 231)   ← ERROR_PIPE_BUSY
   sysroot_std=false
   ```
   注意：这是**创建捕获 stdout 的匿名管道**时就挂了，与 MSVC / 工具链无关。

### 关键判据：探测不稳定

同一个环境、同一台机器，前后两次跑出的结果**不同**：一次 `probe_raw` 报 `os error 231`，另一次探测成功并正常 emit 了 `has_std`。

**说明触发条件没有被隔离出来**（怀疑与并发进程数／管道资源竞争有关，未验证）。
结论不是「怎么让它探测成功」——**而是这个探测不值得被依赖**。

### 修法：把探测**绕开**，而不是修好它

在 `app-ui/src-tauri/Cargo.toml` 里**两个 section 都**显式依赖 indexmap 并打开 `std`：

```toml
[dependencies]
indexmap = { version = "1.9", features = ["std"] }

[build-dependencies]
indexmap = { version = "1.9", features = ["std"] }
```

这样 cargo 会为 indexmap 设置 `CARGO_FEATURE_STD`，`build.rs` 走进 `Some(_)` 分支，**一次 rustc 都不再 spawn**。这也正是 indexmap `build.rs` 注释写的预期用法：
> "If 'std' is explicitly requested, don't bother probing the target for it."

### ⚠️ 为什么必须写**两处**（这是最容易漏的一步）

Cargo **resolver v2**（edition 2021 默认）把 feature 解析拆成两组，**互不合并**：

| 组 | 覆盖 |
|---|---|
| Normal | 普通依赖 + target 依赖 |
| **HostDep** | **`[build-dependencies]` + proc-macro** |

`indexmap 1.9.3` 在这张图里被**编译了两次**（`cargo build -v` 实证）：

| 单元 | features | 来源路径 |
|---|---|---|
| lib `-e9bbbfc74e26ec5d` | `feature="std"` | `tauri-utils → schemars`（Normal 组） |
| lib `-d8fc2bc4f425e407` | `feature="serde","serde-1"` | `tauri-build → schemars`（**HostDep 组**） |

**只在 `[dependencies]` 里开 `std`，修不到 HostDep 那一组**，编译仍会失败。
这是「改完看起来对了、却还在报同样的错」的根因。

### 附带收益

`autocfg` 在整个依赖图里**只有 `indexmap 1.9.3` 一个使用者**（`cargo tree -i autocfg` 已验）。所以这一处修完，编译期就再没有「运行时探测 rustc」这个不确定性来源——**构建结果不再取决于执行环境能不能成功 spawn 子进程**。

### 遗留说明

`indexmap` 是「未使用依赖」：本 crate 不 import 它，只借它触发 feature 统一（unification）。
将来 indexmap 升到 2.x、或 schemars 开始自带 `std` 时，这两行可以整体删除。

## §3 【代码缺陷】Job Object 把刚 spawn 的 Python worker 当场杀掉

> **这一节不是环境问题。** 换任何一台 Windows 机器都会犯，因此优先级最高。

### 症状

终端里能看到 spawn 成功的证据，然后 Python **立刻消失**：

```
[worker] 已 spawn pid=56932 program=...\python.exe cwd=D:\Code\SideProject\Vidnote（来源于 ...）
（然后就没有了：没有 stderr、没有 ready、进程列表里也没有 python.exe）
```

**最难的地方是「什么错都不报」**——进程被 `TerminateProcess` 干掉，来不及写任何输出。

### 根因

`app-ui/src-tauri/src/worker/mod.rs` 里写的是：

```rust
let _job = jobobject::bind_child(&child);   // ← 错在这里
```

`_job` 是**局部变量**，`spawn_worker()` 一返回就被 drop。而 `JobObject::drop` 是 `CloseHandle`，配上创建时设的 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`：

> **关闭本作业的最后一个句柄时，终止作业内所有进程。**

于是这个「防止留孤儿」的保护机制，在 spawn 之后几微秒就**亲手杀掉了刚启动的 worker**。
讽刺点：`jobobject.rs` 的注释本身就把这条语义写对了（"Drop 即关闭句柄……这正是我们想要的"），
但**局部变量让「drop 的时机」变成了「函数返回」而不是「监督器消亡」**。

### 修法

把句柄存进 `Inner`，让它的生命周期与监督器一致：

```rust
struct Inner {
    // ...
    /// 绑定 worker 的 Job Object 句柄。**必须存在这里，不能是局部变量。**
    job: Mutex<Option<jobobject::JobObject>>,
}
```

```rust
let job = jobobject::bind_child(&child);
*self.inner.job.lock().unwrap() = job;
```

句柄只在 `Inner` 被 drop（进程退出路径）时关闭，那时连带终止 worker 正是想要的语义。

### 同类陷阱清单（本模块）

`Drop` 会**产生副作用**的类型，都不可以用 `let _x = ...` 接：

| 类型 | drop 的副作用 |
|---|---|
| `JobObject` | 关闭作业 → **杀掉作业内所有进程** |
| `Child`（std） | 无（std 的 `Child` 不 kill）——但本项目 `Inner::drop` 里**手工** kill |
| `ChildStdin` | 关闭管道 → Python 读到 EOF → 走自杀路径 |

**规则：凡是名字里带「句柄 / guard / 守卫 / 救生圈 / 清理器」的类型，绑定时一律用实名变量，
并在心里回答一句「它什么时候 drop，那时会发生什么」**。用 `_` 前缀等于声明「我不关心它何时死」——
对这种类型恰恰是最危险的。

### 怎么发现的（可复用的排查手法）

第一次读代码时**看不出问题**：`bind_child` 的签名、注释、调用位置都对。
真正的转折是给成功路径补了**一行 spawn 日志**：

```
[worker] 已 spawn pid=56932 ...
```

有了它，就能立刻把问题域从「是不是 locator 找不到解释器 / spawn 失败」收窄到
**「spawn 成功了，但进程马上没了」**，从而怀疑生命周期而不是定位逻辑。

### 顺带修好的可观测性缺口

排查过程中暴露：**状态跃迁在终端里完全不可见**。原来的问题是三重的——

1. `set_state()` 不写日志；
2. 成功路径（spawn 之后、`ready`）**绕过** `set_state` 直接改快照；
3. 文件里有两个几乎相同的发射函数 `emit_state` / `emit_state_locked`，还有一条心跳路径
   直接 `app.emit(STATE_CHANNEL, ..)` 把两者都绕开。

结果是「有的状态跃迁能查到、有的查不到」，现象上极容易误判成「状态机没走到某一步」。

**已合并为唯一发射口 `Inner::emit_state()`**，日志与 `emit` 都在那里，不可能漏记。
现在启动一次能看到完整轨迹：

```
[worker] 已 spawn pid=43332 ...
[worker] state → starting（已启动：…）  alive=true ver=None    gpu=None/None
[worker] state → ready（worker 已就绪） alive=true ver="0.2.0" gpu=true/false
[worker] state → ready（worker 已就绪） alive=true ver="0.2.0" gpu=true/true
```

最后两行就是设计意图：`ready` 先回**快速判据**（`gpu_verified: false`，不阻塞 UI），
异步 CUDA 验证完成后再推 `env_verified` 把 `gpu_verified` 翻成 `true`。
