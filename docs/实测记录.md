## 2.4 基线换代：v1 因缺 `initial_prompt` 记录作废（2026-10-03 实测）

**现象**：用 `app/core/` 正式实现重跑 `samples/video.mp4`，产出 **681 段**，
与基线 `samples/transcript_gpu.txt` 的 **649 段**逐字符比对**失败**。
差异不是内容错误，而是**分段粒度**——基线是整句带标点，重跑产出是碎句无标点：

```
基线   [00:00] 你是不是也干过这种事?听说AI能选股,...,感觉自己马上要财务自由了。   ← 0~14.54s 一段
重跑   [00:00] 你是不是也干过这种事 / [00:01] 听说AI能选股 / [00:02] 兴冲冲打开电脑 / ...  ← 8 段
```

**排查过程（逐步二分，全部为实测）**：

| # | 实验 | 结果 | 排除了什么 |
|---|---|---|---|
| 1 | 5 组 VAD 参数组合：`min_silence_duration_ms` 400/2000 × `condition_on_previous_text` 开/关 × `vad_filter=False` | **全部产出相同分段**，均为碎句 | VAD 与上下文参数 |
| 2 | 用原型脚本 `prototypes/transcribe.py` 跑同一 `audio.wav` | 产出**同样碎句** | 正式实现有差异（即：实现没错） |
| 3 | 环境漂移排查：包安装时间 **18:27** < 基线生成 **19:49**；`models/large-v3/*` mtime 19:49 未变 | 环境未变 | faster-whisper / ctranslate2 / 模型被换 |
| 4 | 音频一致性：重跑 wav = **38528444** 字节 | 与 §2.3 记录完全一致 | 抽音频参数不同 |
| 5 | 加 `--initial-prompt "这是一段关于AI量化交易的讲解，涉及回测、过拟合、夏普比率、特征工程、样本外验证等概念。"` | 前 2 段（0~22.96s）与基线**逐字符一致**（含「夏普3点几」）；总段数 662 vs 649（差 2%） | —— **变量锁定** |

**根因**：基线是用 `prototypes/transcribe.py --initial-prompt "<某段领域术语>"` 产生的
（该脚本 `--initial-prompt` 参数即为此时加；§4 也记录了它的作用）。
但**那个字符串没有落进任何文件**——`config.example.yaml` 是 `initial_prompt: ""`，
`PLAN.md` §5 同为空的，历史会话检索也无记录。

**为什么它不是"调味项"**：`initial_prompt` 不只纠正术语，它会**改变 whisper 的
分段与标点预测**——prompt 本身是一段带标点的完整句子，模型会模仿该风格输出整句。
实测同一音频加/不加 prompt 分别是 **681 段碎句** vs **662 段整句**。
**参数不记录 = 基线不可复现。**

**结论（区分已验证 / 未验证）**：

- ✅ **正式实现正确** —— 与原型脚本在同参数下产出**逐字节完全一致**（24547 字节）
- ✅ **同参数下确定性成立** —— 多次独立运行（含 `--force` 重跑）产出逐字节一致
- ✅ **转写链路全通** —— 下载/抽音频/转写/落库跑通，抽音频 1.5s、转写 2m36s（8.7× 量级），段数可解释
- ❌ **v1 基线不可复现** —— 唯一变量 `initial_prompt` 的值缺失

**处置（2026-10-03，头头决策「定稿 prompt + 重建基线」）**：

1. `initial_prompt` 定稿并写进 `config.example.yaml` 与 `PLAN.md` §5：
   > 这是一段关于AI量化交易的讲解，涉及回测、过拟合、夏普比率、特征工程、样本外验证等概念。
2. v1 基线（649 段）移入 `samples/archive/transcript_gpu_v1_649seg_promptUNRECORDED.*` 留档
3. **用配置模板的原样值**重新生成 v2 基线 → **662 段**，`transcript.txt` = 24547 字节（CRLF）
4. **复现性已实测验证**：两次独立运行，`txt` / `srt` / `json` 三种格式**全部逐字节一致**
5. 参数快照写进 `samples/README.md`——**判据仍是「逐字符严格相等」，只是基线换代，判据未放宽**

**教训（已写进流程与项目约定）**：验收基线必须与**产生它的完整参数**一起存档。
只存产出不存参数，"金标准"就是不可验证的。

### 2.5 阶段 2 调度实测（2026-10-03，真跑 GPU）

**验收输入是刻意造小的**：从 `samples/video.mp4` 用 `-c copy` 切 10 条 60 秒片段（秒级完成）
+ 1 条指向不存在文件的坏链接。理由：这一层要验的是**调度**，不是转写质量（那是阶段 1 的事，
判据是逐字节比对基线）。调度错误与视频长度无关，用 10 条 20 分钟视频只会让每次验收跑半小时。

工具：`tools/phase2_acceptance.py`（`all` 子命令一次跑完 prep → batch → crash → resume）。

| 项 | 实测值 |
|---|---|
| 批量：10 条片段 + 1 条坏链接 | `{'done': 10, 'failed': 1}`，CLI 退出码 **1**，墙钟 **83.1s** |
| 坏链接的处置 | 停在下載阶段，`stage_error` = `[download] 本地文件不存在：…`，其余 10 条不受影响 |
| 峰值并发 | `{'downloading': 8, 'transcribing': 1, 'framing': 1}` |
| 阶段总耗时 / 墙钟 | 90.3s / 82.2s → **重叠系数 1.10×**（1.0 即完全串行） |
| 单条 60 秒片段的三阶段占比 | 下载 ≈ 0.005s（本地硬链接）、抽音频 ≈ 0.07s、转写 ≈ 7s、抽帧 ≈ 1s |

**结论（区分已验证 / 未验证）**：

- ✅ **转写确实是串行瓶颈** —— 峰值并发恒为 1，且占全部阶段耗时约 90%。`PLAN.md` §3.1 的核心判断成立
- ✅ **阶段确实重叠** —— 重叠系数 1.10× > 1.0，不是「每条都很短」造成的假象
- ⚠️ **重叠收益极小，且这是如实结果** —— 能与转写重叠的只有下载与抽帧。60 秒片段上它们合计约 1 秒；
  真实 20 分钟视频的转写占比更高，重叠收益只会**更小**。流水线架构的价值不在「省时间」，
  而在于把不占 GPU 的阶段挪出转写的关键路径，使 GPU 不空转
- ❌ **真实规模的长跑未验证** —— 未做过 100 条 × 20 分钟。内存护栏（可用内存 < 2 GB 时暂停取新任务）
  在真实负载下是否被触发、触发后恢复是否平滑，**未测**。自测脚本用人为压低阈值验过逻辑，但那不是真实负载

#### 断点续跑（进程被强杀）

用 `taskkill /F /T` 强杀整棵进程树（模拟断电 / 任务管理器结束进程），**不是**优雅退出——
优雅退出走的路径本就有清理逻辑，验不出「断电后能不能续」。

| 环节 | 实测 |
|---|---|
| 强杀前 | 跑满 30 秒，PID 51532 |
| 强杀后 DB | `{'done': 3, 'transcribing': 1, 'downloaded': 6, 'failed': 1}` |
| 中途态 | 有 1 条停在 `transcribing`（证明是被硬杀而非优雅退出） |
| 重启日志 | `启动重置：1 条中途态任务已回退` → `已完成，跳过` ×3 → `未完成（downloaded），从断点续跑` ×7 |
| **已完成条目是否被碰过** | ✅ 3 条 done 的 **`status` / `updated_at` / `transcript.txt` mtime 三者均未被改动** |
| 续跑收敛 | ✅ 最终 `{'done': 10, 'failed': 1}` |

**第三条判据是这次验收里最有价值的一条**：只看「最终都 done」证明不了断点续跑——
把它全部重跑一遍也能得到同样的终态。必须比 `updated_at`（数据库层没被重写）
与转写稿 mtime（文件层没被重写），才算真的「没重跑」。

#### 本次验收暴露并修掉的两个真缺陷

| 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|
| `--force` 在 dispatcher 路径下静默失效 | `run samples/video.mp4 --force` 删完产出目录后**一条都不入队**，只留一句「没有任务被入队」 | `dispatcher.submit()` 主动跳过 `done` 状态，而 `--force` 要跑的恰恰是 `done` 的那条 | 入队前把 `done` / `cancelled` 重新盖成 `pending`（对齐 `_run_serial` 的行为） |

## 4. 内容侧发现（影响 `frames.enabled` 的默认值）

对测试视频逐帧过完 212 帧后的结论：

- 画面以 **B-roll 素材 + 硬字幕条**为主
- 全片**没有作者的建模操作演示**
- 出现的平台界面（Backtrader / 聚宽 / QuantConnect）全是第三方素材，不能作为复现依据
- 有独立信息量的帧 **< 15 帧**
- **知识主体 100% 在语音**

**因此 `frames.enabled` 默认为 `false`**，按需开启。这条结论写进配置默认值，不要凭「视频类工具都该抽帧」的直觉改回去。

**交叉校验的价值**：硬字幕条（如 13:34 帧的「做样本外验证」）可用于验证 ASR 分段边界。

同音/近音误识较多，需要术语提示词 + 后处理校正：

## 6. 踩过的坑（详见 `PLAN.md` §9）

按耗时排序，最坑的在前：

1. **CUDA DLL 加载**（约 1 小时，5 次尝试）—— 三层要求缺一不可：
   `add_dll_directory` 句柄保活 + PATH 注入 + 必须在 `import ctranslate2` 之前。
   且 `get_cuda_device_count() == 1` ≠ GPU 可用。
2. **抖音 cookie** —— `yt-dlp --cookies-from-browser` 在 Windows 新版浏览器必然失败
   （Edge：DPAPI 解密失败；Chrome：数据库被占用）。走 playwright-cli → state.json → Netscape 格式。
   `ttwid` 约 24 小时过期。
3. **模型下载** —— HF 直连不通；hf-mirror 对 LFS 文件 302 到 xethub，而 `huggingface_hub`
   默认超时只有 10 秒。可靠做法是 `curl -C -` 手动下载（实测 41 MB/s）。
4. **ffmpeg 9.0 移除 `-vsync`** —— 改 `-fps_mode passthrough`。网上 95% 的教程还是旧写法。
5. **faster-whisper 1.2.1 与 av 19 不兼容** —— `metadata_errors` 参数已移除。
   绕开 PyAV，用 `wave` + `numpy` 直读 wav。
6. **Playwright 自带 ffmpeg 不能用** —— `--disable-everything` 构建，无 mp4 demuxer。
7. **pip 装 CUDA 库** —— PyPI 直连卡死；用国内镜像时**必须加 `--proxy ""`**，
   否则 pip 绕道系统代理反而更慢。清华源实测失败，腾讯云源 1 分 48 秒成功。
